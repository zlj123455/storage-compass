# Q010：存储选型前，业务方必须提供哪些数据？

项目立项会，业务方递过来一张 A4 纸：新系统需要 100TB，三年内可扩展。存储团队接过来看了一眼，问了一个问题："这 100TB 是什么数据的 100TB？"![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdXKMJXthNNXF6pCk2IWibGpPBaZG5lDDohuggSXXPaderB96CwrlicY0Qiczt2YCXUBVYjgrw7rwSp7gKUl4Ric2iaaZ7uibicxO9vtVo/640?wx_fmt=png&from=appmsg)业务方说，就是当前数据量。存储团队把纸放在桌上，说："这不够。下面六份数据，缺任何一份，我们只能比每 TB 单价。"

# 第一份：数据画像

不是"100TB"，而是这 100TB 里有什么。

  1. 数据类型构成及占比（%）：订单数据库、应用日志、图片附件、报表归档——各占多少。不同类型的增长模式、保留策略和保护开销完全不同。
  2. 每类增长模式：线性（注明 TB/月）、突发（注明峰值倍数和触发条件）、还是稳定不增长。只写"三年内可扩展"无法算采购量。
  3. 保留周期（按类型分别写）：订单七年、日志三个月、快照七天、备份四周——保留周期直接决定容量。同一份数据，保留七天和保留三十天，快照增量差三倍以上。
  4. 压缩前提：哪些类型已经压缩过（图片、视频——几乎无法再压），哪些可压缩（文本日志——可达 2-4 倍）。有效容量不是原始容量乘以一个平均压缩率。

不提供：厂商按原始容量报价，保护开销、增长和快照空间全靠猜。买回来发现快照把空间吃掉了 40%，或者压缩率不到预期，只能追加采购。![](https://mmbiz.qpic.cn/mmbiz_png/LF0nGncJCdXX6c3rjy7ic0KVmlkfLqLzzKkvhTmbZib0Qzic8SQYv2ibBC8VJ93N4QXcbOy4YAIydmDIaBbHHyG4obL7pFgX5cX9ibLNNrbAy6G0/640?wx_fmt=png&from=appmsg)一句话理解：100TB 不拆成数据类型和增长模式，采购容量就是猜。

# 第二份：高峰负载

不是"性能要高"，而是最忙的时候在做什么。高峰时段和业务场景：月末结算？早高峰开榜？大促期间？写明时间窗口和持续时间。

  * 读写比例（高峰期）：读 70% 写 30% 还是反过来。读多场景缓存能解决大部分压力，写多场景缓存帮助有限，后端介质才是瓶颈。规格表上的 IOPS 通常用 4KB 随机读测，和 16KB 随机写占 70% 的结算场景差一个数量级。
  * 块大小分布：4KB 小块还是 1MB 大块？小块随机写对 SSD 寿命和控制器压力与大块顺序写完全不同。
  * P99 目标（不是平均值）：P99 通常是平均延迟的 3-10 倍。业务方能接受的 P99 是多少——5ms？20ms？100ms？不知道 P99 目标就无法判断方案是否达标。
  * 后台任务冲突窗口：快照、备份、重建是否和高峰撞在一起？高峰期是否允许暂停某些后台任务？重建期间后端带宽消耗可达 30-50%，前台 P99 可能翻倍。

不提供：厂商用 4KB 随机读、队列深度拉满、无后台任务的空载数字报价。上线后月末一跑，发现 P99 飙到规格表的十倍。![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdUBmtG46xcyKRmdpE11yNiaZ4q9syf3YricPXTCYhWbPcpOSPTFrAGfcKuIyMlo6ZPiaYdkHPqQtLOx77ZI4aJm9r4YIyRJdppP34/640?wx_fmt=png&from=appmsg)一句话理解：性能不是"月末忙"三个字，而是读写比例、块大小、P99 和后台冲突的具体数字。

# 第三份：恢复要求

不是"有备份就行"，而是每种故障下要恢复到什么程度。

  * 按故障类型分别定义 RPO/RTO：
  * 恢复优先级和依赖链：订单库、日志库、报表库同时挂了，先恢复哪个？数据库需要日志先 replay，应用需要数据库先恢复，报表可以最后。顺序错了，即使每个组件都能恢复，整体时间也会拉长。
  * 降级容忍度：重建期间性能会降级。业务方能接受降级运行还是必须完全停服？降级运行的话 P99 能接受到多少？能接受多长时间？

不提供：厂商承诺"支持快照和备份"，但不承诺在约定时间内按正确顺序把正确业务恢复到可用状态。出了故障才发现恢复顺序不对、降级太严重、RPO 远超预期。![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdWEK1lZFKGeOdlst1BxhFyaLFUVXuB0TqAbcOlO6Eq1ia3ZH2UxcvRLA0WR5sg3GemJEreAZejiayQNxiagBx0ia2zX0A3vrQ0WgN0/640?wx_fmt=png&from=appmsg)一句话理解：恢复不是有一份副本，而是按故障类型分别定义时间目标、恢复顺序和降级容忍度。

# 第四份：容量约束

不是"三年可扩展"，而是怎么扩、扩多少、什么时候扩。年增长量（TB/年）：根据数据画像的各类增长模式推算。扩容颗粒不应超过年增长量的 2 倍——年增 20TB 的业务一次买 100TB 意味着 80TB 在闲置。扩容方式：加盘还是加节点？加盘的话一次最少加多少？加节点的话网络和许可证是否支持？扩容是否需要停机窗口？预留余量：采购容量通常预留 15-25% 给重建和碎片。低于这个阈值，重建时性能急剧下降。不提供：买回来到第一次扩容的间隔要么太短（颗粒太小频繁停机），要么资金占用过大（一次买太多闲置）。![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdVZERERB5NqLevYmSPj40XhQu3NN27SDgEVGM88fdajdX4Q4K6ibVG2miavI9taT9nBWqQVszsRAF0MYYnMm61ic5XI99L045k6QY/640?wx_fmt=png&from=appmsg)一句话理解："三年可扩展"不是需求，年增长量、扩容颗粒和预留余量才是。

# 第五份：运维边界

不是"厂商支持"，而是谁干什么、什么时间干、出问题找谁。维护窗口：什么时间可以停机——凌晨？周末？还是完全不能停？升级和扩容只能在这个窗口内完成。升级兼容矩阵：固件版本、多路径软件、集群协议版本、上层应用驱动——升级前必须验证。能否回退？回退窗口多长？告警分级和接收人：SMART 告警到实际故障的窗口差异很大——坏道增长型可能数周到数月，电机或磁头故障可能数小时。哪些告警走值班、哪些走工单、哪些直接打电话？迁移方案（三年后换平台）：双写最安全但需要 2 倍容量和带宽；不双写的话切换窗口能停多久？迁移工具和回退方案由谁提供？不提供：方案第一天能上线，第一次升级发现兼容性问题、第一次扩容发现要停机、第一次告警发现没人知道该找谁。![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdU1M2p1KxnxicBslicZnKHg7MyiaDNWeRp2xlicBC54JEjQvWAxhuTeOiaibOEcy4CtL4YtQNpnvqPFx6R9MaNDHL2eJ5h9lTtU7ZKl8/640?wx_fmt=png&from=appmsg)一句话理解：方案不是设备交付即结束，而是扩容、升级、告警和迁移每一项都有人负责才算兑现。

# 第六份：业务后果声明

不是所有数据都需要上面五份全部填满。数据重要性分级：哪些是交易关键数据（丢了赔钱）？哪些是可重建数据（丢了能恢复）？哪些是可丢弃数据（丢了无所谓）？可接受的简化后果：对可重建或可丢弃的数据，业务方明确接受：更长的 RTO、更低的保护等级、更简单的方案。不是没填表就算简化，而是填了之后判断哪些可以降级。对可丢弃、可重建、单一团队使用的数据，需求可以简化。但只要数据跨团队共享、承载交易或生产服务、需要跨故障域恢复，前面五份就不能省。不提供：所有数据按同一等级保护——要么过度保护浪费成本，要么保护不足出事才发现。![](https://mmbiz.qpic.cn/mmbiz_png/LF0nGncJCdV0rm6lK1CchKVHRQk6piaibath6h4CUgTMxeiafKWQtqzzgeO04Vu1Up9v4cBiacHNu87GUKyYXZVevmKcWlzfweauHWdqQQb4Ta4/640?wx_fmt=png&from=appmsg)一句话理解：简化不是省略，而是填完之后知道哪些可以降级、哪些不能。

# 交表之后

架构师把六份模板装订在一起，交给业务方："填完这张表，再找厂商。"厂商拿到的不再是"100TB、性能要高、有备份"，而是：数据类型构成、高峰读写比例和 P99、按故障类型分的恢复目标、年增长量和扩容约束、维护窗口和升级兼容要求、数据重要性分级。PoC 也因此改变——不再是演示空载规格，而是用业务方提供的数据，在真实高峰、后台并发、容量逼近和故障恢复场景下，证明业务目标是否仍能满足。100TB 从来不是需求本身。它只是业务事实还没有被说清时，最容易写下的那个数字。
