# Q036：全闪存阵列的性能瓶颈通常在哪里？

> 来源：存储罗盘（微信公众号）  
> 原文链接：https://mp.weixin.qq.com/s/-abZSlZ2H3rA7qmHFc0jlg
> 发表时间：
> 迁移时间：2026-10-25

假设一套数据库迁入全闪存阵列。普通时段，查询和提交都比原来快；到了月末高峰，写入 P99——99% 请求不超过的时延——却从平稳变成连续尖峰。运维看到阵列前端带宽没有跑满，平均 CPU 也没有到 100%，于是把怀疑重新放到 SSD 上。

仅凭带宽和平均 CPU，还不能判断问题是否出在 SSD。全闪阵列缩短了介质访问时间，却没有消除排队、数据处理、冗余写入和后台恢复。真正的瓶颈，是某一环节的持续完成能力已经跟不上请求压力。

因此，排查全闪性能不能只问“盘够不够快”，而要沿着慢请求寻找：等待从哪里增加，后续环节的完成速率有没有下降，是否已经触发反压或限流。

# 请求还没进入阵列，就可能已经在等

一次数据库写入离开应用后，还要经过文件系统或裸设备、主机块层、驱动、HBA 或网卡、多路径以及交换网络，才能到达阵列前端端口。

Linux 的多队列块层会尝试把请求直接提交给硬件；需要调度或合并时，请求可能先进入软件暂存队列。当硬件暂时没有资源接收更多请求时，请求也会留在派发队列等待。换句话说，应用看到的存储时延，可能包含阵列尚未开始计时的主机侧排队。

这也解释了一个常见现象：阵列总带宽还有余量，某台主机仍然很慢。拥塞可能只发生在一条路径、一个端口或一个队列上；其他端口空闲，并不能替这条路径完成请求。多路径数量也不等于流量一定均衡，实际分布还取决于主机策略、连接归属和工作负载。

排查时要把同一时间窗口内的应用时延、主机未完成 I/O、各路径流量和阵列前端服务时延放在一起看。若主机等待持续增加，而阵列记录的服务时延相对稳定，线索应先留在主机与连接这一段。

# 进入控制器后，闪存还没有开始工作

请求到达阵列，不会立即变成一次 NAND 访问。控制器可能需要查找逻辑地址映射、判断缓存命中、分配空间、维护元数据，再按配置执行压缩、去重、校验、加密或副本处理。

这些工作有些按字节消耗资源，有些按 I/O 次数消耗资源。相同的 1 GiB/s，若由 1 MiB 请求组成，大约每秒一千次操作；若由 4 KiB 请求组成，则是约二十六万次。这里只是按前端请求大小进行的数量换算，不代表后端实际 I/O 次数，但它说明了为什么带宽相同，控制器承担的逐请求工作可以相差两个数量级。

平均 CPU 利用率也可能掩盖局部饱和。某个控制器节点、处理核、工作队列或热点卷已经繁忙，其他资源仍然空闲，平均值看上去就“不高”。此时继续增加并发，吞吐不再明显增长，新增请求主要变成等待；少量慢请求可能先体现在 P99 上，平均时延却仍不显眼。

真正有用的证据不是一张整机 CPU 曲线，而是慢请求是否集中在同一节点、端口、卷或数据服务阶段，以及对应队列是否同步增长。

# 缓存让突发更快，也会把瓶颈推迟出现

许多阵列会在数据进入受保护缓存后向主机确认，再把数据写往后端。这样做可以吸收短时突发、合并相邻写入，并把零散的小写转成更高效的后端操作。

Linux MD 的写回缓存提供了一个公开例子：它能聚合零散写入，形成完整条带后再写往 RAID 成员，从而减少部分旧数据读取。企业阵列的实现各不相同，但缓存改变前台确认与后端工作的时间关系，这个机制是相通的。

缓存通过合并写入，可能提高后端的有效吞吐，但容量终究有限，无法长期吸收超过优化后写出能力的流量。假设高峰期每秒进入缓存的数据长期多于后端能够写出的数据，待写量就会不断积累。当可用缓存接近产品设定的保护阈值时，常见实现会延迟或限制新的写入，为后端争取时间。业务可能先经历一段快速写入，随后看到时延持续抬升或周期性波动。

如果开场中的月末高峰不是一开始就慢，而是持续写入一段时间后才恶化，工程师就应把缓存待写量加入时间线。扩充缓存或许能延长快速阶段，却未必改变长时间运行后的稳态性能。应同时观察前端写入速率、缓存占用或待写量、后端写出速率，以及限流开始的时间。若待写量与业务时延一起上升，就应重点检查写出路径，再用后端完成速率和资源状态确认限制发生在哪里。

# SSD 本身也有稳态和后台工作

数据到达后端后，SSD 仍需处理闪存转换层映射、垃圾回收、磨损均衡和内部并行调度。空盘或刚安全擦除后的短册，可能拥有大量可直接写入的空闲页；持续覆盖写入后，设备需要搬移仍然有效的数据并回收擦除块，响应时间可能进入另一个状态。

SNIA 的固态存储性能测试规范要求按工作负载进行预处理并进入稳态，还专门包含持续写入和垃圾回收影响测试。这说明“刚开始跑出的峰值”与“长时间运行的可持续表现”需要分开验证。

阵列后端还可能同时执行校验更新、数据整理、介质巡检和故障重建。它们会与前台 I/O 争用 SSD、后端链路和控制器处理能力。某个成员偶发变慢时，需要等待多个成员完成的写入或重构读取，也可能被最慢的一侧拉长。

因此，判断“SSD 是不是瓶颈”不能只看平均利用率。还要看成员级繁忙度、后端时延分布、写放大迹象、垃圾回收或恢复任务，以及前端一笔 I/O 被转换成多少后端工作。

# 回到那次月末高峰

沿着请求路径复盘，团队可以把几种现象分开：

同时出现的现象| 优先追查的位置  
---|---  
主机未完成 I/O 增长，阵列服务时延较稳定| 主机队列、路径和前端连接  
数据处理时延升高，压力集中在某节点或卷| 控制器处理、热点与共享资源  
持续写入后待写量增加，随后前台时延上升| 缓存写出和后端持续处理能力  
故障恢复或后台任务期间 P99 明显抬升| 前后台资源竞争与限速策略  
预处理后性能下降并进入新的稳定区间| SSD 稳态、垃圾回收及写放大  
![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdWpCqCK5iaSYoP2bLlkNTzmn8zHEC4S7LuouXt33qYYySJ4Q4IYd7URvXH7Ec8AoX1rWW6OB6AyZx3zwmPXVChtK87o1aue7oxI/640?wx_fmt=png&from=appmsg)

这张表提供的是排查方向，不能凭单个指标直接定责。不同产品对“主机时延”“阵列时延”和“后端时延”的统计起止点并不一致，采样周期也可能不同。对比之前，应先确认指标定义并对齐时间。

如果只能保留一个判断方法，我会选择追踪等待在哪里增加，以及对应环节的完成速率怎样变化。第一个增长的队列很有价值，但它也可能只是下游变慢后形成的上游积压；有些产品还会通过反压或队列深度限制，让队列看起来没有继续增长。

所以，给全闪阵列加盘、加端口或加控制器之前，应先回答：慢请求具体等在哪一段，是什么限制了后续完成速率，新增资源能不能解除这个限制？没有这条证据，再昂贵的升级也可能只是增加了尚未被使用的资源。
