# Q002：NAS、SAN 与对象存储的差别是什么？

## 业务场景

一个文件共享、数据库和备份系统同时增长的团队，常会问：“NAS、SAN 和对象存储，哪一种更专业？”真正需要先解决的不是接口名称，而是业务到底需要文件语义、块设备语义，还是通过 API 访问海量对象。

## 核心结论

NAS、SAN 与对象存储不是同一层面的三种“容量套餐”，它们分别提供文件、块和对象访问方式。选型应从应用如何读写数据、如何处理一致性和如何恢复开始，而不是从设备价格开始。

## 架构或机制

### NAS：应用看到的是文件和目录

NAS 通常通过文件协议提供共享目录、权限、文件锁和目录命名空间。办公文件、共享素材和需要多客户端访问的文件业务，往往更容易直接使用这种模型。风险在于目录遍历、锁竞争和大量小文件会把元数据操作放大。

### SAN：主机看到的是块设备

SAN 把块设备交给主机，由主机文件系统、数据库或虚拟化平台决定如何组织数据。它适合需要稳定块设备语义、由应用控制文件系统或卷管理的负载，但主机多路径、集群文件系统和故障切换也要由架构师验证。

### 对象存储：应用通过 API 管理对象

对象存储把数据、元数据和对象键放在 API 模型里，适合备份、归档、数据湖和海量非结构化数据。它的边界也很清楚：不能假设所有需要随机覆盖、文件锁或低延迟同步写入的应用都能直接迁移过去。

## 关键取舍

文件语义更直观，但目录和锁的规模会影响性能；块语义更接近数据库和虚拟化平台，但主机侧运维责任更大；对象语义更适合横向扩展和生命周期管理，但应用通常需要适配 API、分片和一致性模型。

## 适用边界

如果业务只有简单文件共享，NAS 可能足够；如果应用明确要求块设备，SAN 或云块存储更自然；如果数据主要是备份、归档或数据集，对象存储更值得优先评估。混用接口时，应明确数据复制、权限和恢复路径，不能只因为容量相同就互相替代。

## 证据与参考

本文是基于三种访问语义的通用架构判断，不绑定具体厂商。最终选择需要用真实应用协议、并发、时延、恢复和权限场景做 PoC 验证。
