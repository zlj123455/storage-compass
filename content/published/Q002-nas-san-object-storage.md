# Q002：NAS、SAN 与对象存储的差别是什么？

## 业务场景

一家制造企业把部门文件、ERP 数据库备份和产品图片放在同一个“共享存储”项目里。采购讨论一开始只比较容量和价格，后来才发现三个问题：文件服务需要目录、权限和锁；数据库备份需要连续写入和可恢复的块或对象；产品图片又希望低成本保存、按标签检索。它们都叫“数据”，但访问语义完全不同。

如果把三类数据都当作文件，数据库备份可能受目录和小文件操作影响；如果把所有数据都当作块设备，主机侧文件系统、卷管理和故障切换责任会变重；如果把所有数据都迁到对象存储，应用对随机覆盖、文件锁或同步写入的假设可能失效。

## 核心结论

NAS、SAN 与对象存储不是三种同层级的容量套餐，而是三种不同的数据访问语义：NAS 把文件和目录交给客户端，SAN 把块设备交给主机，对象存储把对象和元数据交给 API。选型必须先回答“应用如何读写、如何恢复、谁负责一致性”，再讨论设备型号和介质。

## 架构或机制

### NAS 解决的是共享文件语义

NAS 的价值不只是把磁盘挂到网络上，而是提供目录、文件属性、权限、锁和共享命名空间。多个客户端可以看到同一套文件树，应用通常不需要自己实现这些能力。

代价是元数据路径会成为独立的性能变量。目录遍历、权限检查、打开关闭文件和锁竞争，可能在链路带宽跑不满时就把时延推高。海量小文件、深层目录和大量并发客户端尤其需要单独观测。

### SAN 解决的是主机控制块设备

SAN 把卷或逻辑块设备交给主机，文件系统、数据库或虚拟化平台决定数据如何组织。它适合需要稳定块设备语义、由应用控制写入顺序或由集群软件管理卷的负载。

但责任也随之向主机侧移动：多路径是否正确，主机看到的设备标识是否稳定，故障切换时文件系统是否安全，卷扩容和快照是否被应用理解，都需要运维团队验证。存储阵列提供了冗余，并不代表主机路径自动可靠。

### 对象存储解决的是 API 化的数据管理

对象存储把对象、键和元数据作为 API 资源管理，适合备份、归档、数据湖、模型数据集和生命周期管理。对象通常以完整对象或分片方式写入，应用可以按标签、前缀和保留策略组织数据。

它的边界同样明确：如果应用需要频繁原地覆盖、严格文件锁、目录级原子改名或极低延迟同步写入，直接把文件路径替换成对象键通常不够。需要通过网关、适配层或重新设计数据布局，不能只改一个挂载点。

### 三种语义不能用“容量相同”互相替代

| 关注点 | NAS | SAN | 对象存储 |
|---|---|---|---|
| 应用看到的接口 | 文件和目录 | 块设备 | API、对象键和元数据 |
| 一致性责任 | 协议与文件服务共同承担 | 主机文件系统或应用承担更多 | API 与应用数据模型共同承担 |
| 典型压力 | 元数据、锁、目录并发 | 主机队列、多路径、同步写 | 大对象吞吐、请求并发、生命周期 |
| 适合优先评估 | 文件共享、协作目录 | 数据库、虚拟化、块应用 | 备份、归档、数据湖、数据集 |

## 关键取舍

选择 NAS，通常是用较直观的文件语义换取对元数据和权限治理的要求；选择 SAN，是用主机侧的控制能力换取更贴近块设备的应用整合；选择对象存储，是用 API 和数据布局适配换取横向扩展、生命周期和容量成本优势。

真正的决策顺序应是：

1. 应用是否依赖文件锁、目录、原子改名或随机覆盖？
2. 写入确认必须满足什么持久化条件，丢失一个请求的后果是什么？
3. 数据是高频在线访问、周期性备份，还是长期归档？
4. 故障时由哪一层负责重试、切换、回滚和恢复？
5. 权限、审计、保留和跨站点复制应由协议、应用还是平台承担？

## 验证方法

不要用一个综合分数验证三种接口。文件业务应测目录遍历、锁竞争和多客户端并发；块业务应测同步写、队列深度、多路径切换和文件系统恢复；对象业务应测分片上传、并发 GET/PUT、生命周期转换、删除保护和恢复演练。

验收记录至少要包含：业务请求类型、并发度、平均与 P99 延迟、故障切换表现、恢复目标、权限结果和数据完整性。若只记录顺序吞吐，三种接口都可能得到一个漂亮但无法解释生产问题的数字。

## 适用边界

简单文件共享不必为了“专业”强行引入块或对象接口；可从源头重建的临时数据，也不必一开始就建设复杂的多接口架构。相反，关键交易、海量对象、跨站点恢复和多租户权限一旦成为硬约束，就应把访问语义和故障域一起设计。

## 证据与参考

本文使用的是协议与数据模型的通用架构判断，不绑定具体厂商。具体阈值、兼容性和恢复结果需要使用生产负载或等价 PoC 验证；若应用的接口假设没有文档或测试支撑，应把它标为待确认项。
