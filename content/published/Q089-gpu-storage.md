# Q089：GPU 工作负载为什么需要重新审视存储？

## 业务场景

一个训练集已经放进存储系统，但 GPU 利用率仍然忽高忽低：数据准备进程在读取样本，训练进程在等待批次，检查点写入又在同一时间制造高峰。此时再只增加 GPU，未必能缩短训练时间。

## 核心结论

GPU 工作负载需要重新审视存储，是因为训练效率取决于数据准备、并行读取、检查点写入和元数据访问能否持续供给，而不是只取决于存储的峰值带宽。

## 架构或机制

### 数据准备决定 GPU 能否持续取数

训练前的数据清洗、解码、切片和格式转换可能产生大量小文件和随机访问。存储端即使能提供很高的顺序吞吐，目录遍历、打开关闭文件和随机读取仍可能成为瓶颈。

### 检查点会制造周期性写入高峰

训练过程需要保存检查点，以便故障后恢复或在不同阶段评估模型。检查点写入与数据读取争用带宽、缓存和队列，若没有隔离策略，保存动作可能让训练和其他业务同时抖动。

### 并行度必须和数据路径一起设计

多个训练进程、节点和数据加载器会同时访问存储。网络路径、客户端连接数、元数据服务和缓存策略都可能限制并行度；单个客户端的带宽数字不能代表整个训练集群的实际供给。

## 关键取舍

全闪可以降低时延并提高小文件处理能力，但成本和容量规划压力更高；容量型或对象存储适合大规模数据集和归档，但通常需要缓存、预取或数据分层来减少训练路径上的随机访问。把训练数据、检查点和长期归档混在同一资源池里，运维简单，却更容易互相干扰。

## 适用边界

数据集较小、训练频率低、数据可在本地缓存的团队，不一定需要专门的并行存储。只有当 GPU 等待数据、检查点窗口过长或多节点并发明显争用时，存储侧投入才值得用端到端测量来验证。

## 证据与参考

本文使用的是 GPU 数据管道的通用故障模式，不假设具体模型或产品。验证时应同时记录 GPU 利用率、数据加载等待、存储队列、元数据操作和检查点耗时。
