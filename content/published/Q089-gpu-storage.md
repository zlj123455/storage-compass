# Q089：GPU 工作负载为什么需要重新审视存储？

## 业务场景

一个训练集群已经扩容了 GPU，但训练吞吐没有按比例增长：有些批次开始时 GPU 利用率很高，运行一段时间后却周期性掉到低位；检查点保存时，所有节点同时出现等待；数据准备任务还把目录遍历和中间文件写入挤进了训练路径。

这种现象很容易被误判成“GPU 调度不好”。如果 GPU 在等待数据加载、解码、网络传输或检查点落盘，增加计算卡只会让等待的计算资源更多。此时应该从端到端数据路径重新检查存储，而不是只看阵列宣传的峰值带宽。

## 核心结论

GPU 工作负载需要重新审视存储，是因为训练效率取决于数据准备、并行读取、检查点写入、元数据访问和故障恢复能否持续供给。存储系统要满足的不是一个峰值吞吐数字，而是整个训练周期内可预测的供给能力。

## 架构或机制

### GPU 等待的可能不是带宽，而是数据路径中的空洞

训练通常包含数据索引、样本读取、解码或增强、批次组装和传给 GPU 几个阶段。任一阶段速度不稳定，都会把等待传递到计算卡。顺序大文件读取可能很快，但如果数据集由大量小文件组成，元数据操作和随机读取会先达到瓶颈。

诊断时要把“存储没有跑满”和“数据没有及时到达”区分开。应用侧应记录数据加载等待、批次准备时间和 GPU 空闲区间；存储侧应同时观察元数据请求、读写队列、客户端并发和网络重传。

### 并行读取需要多层同时扩展

多节点训练会同时访问同一数据集。客户端 worker 数量增加后，请求可能集中到少数目录、元数据服务或网络路径；存储后端有足够带宽，不代表每个客户端都能获得稳定的服务时间。

并行设计还要回答两个问题：数据是否可以被本地缓存或预取，缓存失效后重新读取是否会形成同步风暴；不同训练任务是否共享同一个故障域和 QoS 池。没有这两项约束，横向扩展很容易变成请求放大。

### 检查点是周期性写入压力，不是普通归档

检查点写入往往集中发生，并且具有恢复价值。训练任务需要知道写入何时可安全确认，运维团队则要知道故障后从哪个检查点恢复、保留多少版本、跨站点复制是否必须完成。

如果检查点与训练数据共享队列，保存动作会改变前台读取延迟；如果为了缩短保存时间而牺牲一致性，故障恢复时可能得到不完整的状态。存储设计应将“写得快”和“恢复得对”分开验证。

### 故障恢复也会反过来影响训练效率

训练系统常会重试读取、重新预热缓存或从最近检查点恢复。存储发生路径切换、节点故障或后台重建时，恢复流量可能与正常训练争用资源。若只测健康状态下的吞吐，无法判断一次故障会让训练停多久。

## 关键取舍

全闪或高性能文件服务可以降低随机读和元数据等待，但采购、能耗与容量成本更高；容量型或对象存储适合保存大规模数据集和长期版本，却往往需要节点缓存、预取、数据打包或分层来保护训练路径。

把训练数据、检查点和归档数据放在同一池中，管理对象少，但 QoS 和故障隔离更难；拆分资源池能形成清晰的性能承诺，却会增加复制、容量和运维边界。真正要比较的是一次训练周期的有效吞吐、恢复时间和总成本，不是单次压测峰值。

## 验证方法

PoC 至少应包含四种状态：正常训练、检查点写入、数据准备并发运行、存储路径或节点故障。每种状态都记录：

- GPU 利用率、数据加载等待和批次准备时间；
- 客户端读写吞吐、请求大小、队列深度和 P99 延迟；
- 元数据请求量、目录热点、缓存命中与网络重传；
- 检查点完成时间、可恢复性和从故障到训练继续的时间。

如果这些指标没有同时采集，测试结果只能说明某一层的能力，不能证明存储系统支撑了训练工作负载。

## 适用边界

数据集较小、训练频率低、样本可以完整放入节点本地缓存的团队，不一定需要专门的并行存储。只有当 GPU 等待数据、检查点窗口过长、节点并发扩大或故障恢复目标明确时，存储侧投入才值得用端到端测量来验证。

## 证据与参考

本文基于 GPU 数据管道中常见的等待、并行和检查点故障模式，不假设具体模型、框架或产品。生产判断应以训练日志、存储观测和故障演练结果为证据；缺少实测的阈值应明确标为假设。
