# Q033：写入确认发生在缓存、日志和磁盘的哪个阶段？

凌晨，订单系统完成了一笔支付。应用日志记录“事务提交成功”，但存储监控里仍有一批数据等待回写。值班工程师盯着这两个状态，产生了一个很自然的疑问：数据还没写到 SSD，数据库凭什么告诉用户成功？

这两个状态并不一定矛盾。“写入成功”不是存储路径上唯一的时间点，而是某一层确认自己已经满足了约定的完成条件。操作系统接收数据、数据库提交事务、阵列确认写入和数据最终回写到介质，代表四份不同的承诺。

真正需要追问的是：谁返回了成功？恢复这笔业务所需的信息保存在哪里？这份承诺能抵御进程崩溃、主机掉电、控制器故障，还是整个站点故障？

下面假设这是一个正常开启持久化保障、采用本地同步提交的数据库。不同数据库和配置可能改变确认位置，但分析方法相同。

# 第一声“成功”，可能只是内核接收了数据

应用调用普通的write()写文件时，数据通常会先进入操作系统管理的内存缓存。调用返回，只说明内核接受了这些字节，并不保证它们已经进入非易失存储。Linux 的write(2)手册对此写得很直接：成功返回不保证数据已经提交到磁盘，部分错误甚至可能延迟到后续写入、关闭文件或同步时才暴露。

这不是系统偷懒，而是缓存和合并写入带来的正常性能机制。如果每个几 KB 的修改都必须独立等待介质完成，许多业务的写延迟会明显增加。

问题在于，上层不能把“已接受”误读成“可恢复”。如果应用自己维护关键文件，就要使用与持久化目标相符的同步机制；如果应用把事务交给数据库，则应该由数据库定义何时可以返回提交成功。

# 数据页还没落盘，事务为什么仍能提交？

一笔订单可能修改订单表、库存、账户余额和多个索引页。如果提交必须等待所有数据页逐一写完，延迟高，而且故障发生在写到一半时，磁盘上还可能留下互相不匹配的页面。

数据库通常借助预写日志解决这个问题。以 PostgreSQL 的 WAL（Write-Ahead Logging，预写日志）为例，描述数据修改的日志记录必须先于对应数据页进入持久存储。事务提交时，数据库重点保证恢复所需的 WAL 已经持久化；被修改的数据页可以随后由后台写回。

因此，最终数据页尚未全部落盘，不等于已确认事务无法恢复。主机此时崩溃，数据库重新启动后可以读取 WAL，把尚未写入数据页的修改重新执行，也就是 REDO。

反过来，WAL 只写进数据库进程缓冲区或操作系统页缓存仍然不够。若数据库已经回复提交成功，而相应日志在掉电后消失，这笔事务就失去了重做依据。本文所谓“本地同步提交”，指数据库要等待该事务所需的本地 WAL 达到其持久化条件；异步提交以及等待远端副本确认，是另外的承诺。

# 持久化要求怎样穿过文件系统和块层？

数据库不能直接观察每一颗闪存芯片。它只能通过操作系统接口表达要求，例如对 WAL 文件执行fsync()，让文件数据及恢复访问它所需的元数据进入持久存储。

请求继续向下时，还要面对设备或控制器的易失写缓存。Linux 块层为此定义了缓存刷新和 FUA（Force Unit Access，强制单元访问）等机制：刷新用于推动此前已完成的写入离开易失缓存；带 FUA 的请求只有在该请求的数据进入非易失存储后，才能报告完成。

但 FUA 不是一句“所有数据都已落盘”，也不会自动建立所有请求之间的顺序。文件系统和数据库仍需按正确次序发出写入与同步请求，驱动、控制器和设备也必须正确传递并执行这些语义。路径中任何一层虚假地提前确认，上层建立的 WAL 顺序就可能只存在于逻辑上。

# 阵列在 SSD 之前确认，算不算真的完成？

日志请求到达存储阵列后，控制器可能先把数据放入写缓存，再向主机返回完成。这里不能只看“缓存”两个字，而要判断它是不是这套系统定义的非易失保护域。

如果缓存只存在于普通内存，整机断电就可能让已确认写入消失。如果数据只保存在一个控制器中，单控制器故障也可能使伙伴控制器无法继续履行承诺。企业阵列常用电池或电容保护、非易失存储以及控制器间缓存镜像覆盖这些风险，但每项机制保护的故障不同，不能互相替代。

在保护状态正常、持久化命令被正确处理，并且故障没有超出产品承诺范围的前提下，数据进入受保护写缓存后就可以满足主机所要求的本地持久化条件，不必等待它立刻写到最终 SSD。之后的后台回写是在兑现阵列内部责任，不等于数据库事务仍未提交。

还要分清数据库 WAL 与阵列内部日志：WAL 知道事务如何重做，阵列只知道哪些块写入已经被确认。阵列无法判断某些块属于订单、索引还是半笔业务事务，数据库也不会因为阵列有写缓存，就自动获得异地副本或备份。

# “提交成功”究竟覆盖了哪类故障？

回到开头那笔订单，可以沿故障范围逐层判断。

数据库进程崩溃，但主机和存储仍在，已经持久化的 WAL 可以用于崩溃恢复。主机突然掉电，如果日志只在主机内存中就会丢失；如果它已经到达能够抵御掉电的本地持久化域，数据库重启后仍有恢复依据。

阵列单控制器故障时，能否保住已确认写入，要看缓存是否按设计镜像、伙伴控制器是否具备正确状态并能接管。整个机房丢失时，本地受保护缓存和最终 SSD 可能一起不可用；除非提交条件还明确等待了远端系统，否则“本地提交成功”不能推导出跨站点零数据丢失。

还有一种容易被忽视的情况：数据库已经提交，成功响应却在返回途中丢失。客户端看到超时，并不知道事务是失败还是已经完成。此时盲目重试可能产生重复订单，业务需要通过事务查询、唯一约束或幂等设计处理这种“不确定结果”。存储持久化无法替应用解决重复提交。

# 下次看到“写成功”，继续问三件事

不要先争论数据到底算不算“落盘”。先确认返回成功的是系统调用、数据库、控制器还是远端副本；再确认恢复所需的是最终数据页、事务日志，还是两者的特定顺序；最后写清承诺覆盖的故障域，以及保护组件降级后确认路径会不会改变。

一笔写入真正的完成点，不由“缓存、日志、磁盘”这几个名词决定，而由恢复协议决定：发生约定范围内的故障后，系统是否仍保存了足够且顺序正确的信息，能够恢复到它已经向业务承诺的状态。
