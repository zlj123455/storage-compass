# Q003：一个 IO 请求进入存储系统后发生了什么？

## 业务场景

应用日志显示一次读取耗时变长，团队却只看到“磁盘利用率不高”。要解释这个现象，需要把一次 IO 从应用发出到数据返回的路径拆开，而不是把所有延迟都归因于介质。

## 核心结论

一个 IO 请求通常会经过应用和文件系统、客户端缓存、协议与网络、存储控制器、缓存或介质，最后沿着返回路径把结果交给应用。任何一层的排队、重试、一致性等待或故障切换，都可能改变最终时延。

## 架构或机制

### 应用先决定请求的形状

数据库日志、虚拟机磁盘和文件服务会产生不同大小、不同顺序性和不同同步要求的请求。应用的并发、读写比例和是否等待持久化确认，决定了后续路径要处理什么工作。

### 客户端与协议路径会改变排队

文件系统、卷管理、缓存、多路径和协议栈会增加队列，也可能在路径异常时重试或切换。网络拥塞、丢包和链路不均衡并不一定表现为磁盘忙，却会直接扩大端到端延迟。

### 控制器、缓存与介质决定完成语义

控制器可能进行缓存、校验、数据缩减、条带化或后台重建。写入何时被确认，取决于系统是否已经满足应用要求的持久化条件；后台任务和故障恢复也会与前台 IO 竞争资源。

## 关键取舍

缓存可以降低常见路径的等待，但需要明确断电保护、一致性和失效后的行为；更高的并发可以提高吞吐，却可能放大队列深度和尾延迟。排查时应同时观察应用时延、协议路径、队列、控制器和介质，而不是只看某一个百分比。

## 适用边界

不同系统对缓存、同步写和故障切换的实现并不相同。本文用于建立端到端排查框架，不能替代具体平台的路径图、日志和故障演练。

## 证据与参考

这是一个与协议和设备品牌无关的通用 IO 路径模型。生产判断应使用一次真实请求的时间线、路径状态和各层延迟数据进行验证。
