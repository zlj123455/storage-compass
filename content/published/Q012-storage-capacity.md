# Q012：存储的可用容量为什么常常小于采购容量？

> 来源：存储罗盘（微信公众号）  
> 原文链接：https://mp.weixin.qq.com/s/xTmv_A6cqH1JwMClVz6NRg
> 发表时间：
> 迁移时间：2026-10-25

一套新全闪阵列采购完成，项目组把所有 SSD 标称容量相加，得到 500TB。半年后，业务数据只写入了约一半，运维却要求尽快扩容，并限制再创建快照。

业务方不解：500TB 全闪才用了不到一半，为什么就告急了？

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdWA7mhvKEHxlPyLd22yicEMzeqL8OcD41cVaYDeEKTFWR55RVjAS6fvhkMDIjFd3ibt1lwU7F9b5UXThKqak3yJ2DmiaiaSCyf5nK4/640?wx_fmt=png&from=appmsg)

存储团队说：采购时的 500TB、报价单上的"可用容量"、系统里实际能分配给业务的空间，往往不是同一个东西。把它们压成一个数字，系统就会在最不该缺空间的时候缺空间——扩容、重建、快照保留或故障恢复期间。

采购容量不是可用容量；可用容量也不是可承诺给业务的容量。真正可以承诺的空间，要同时扣除保护开销，并留下增长、变更和故障恢复的落点。

# 三种容量别混在一张报价单里

业务方拿出报价单：上面写着"500TB 可用"。

存储团队说，先拆成三个口径。

最底层是物理容量：所有闪存介质的标称容量之和。闪存盘的标称容量和用户可访问容量之间还隔着 OP（超额预留空间），厂商用这部分空间做磨损均衡、坏块替换和垃圾回收，不纳入可用容量。

往上是经过 RAID、纠删码或副本策略后的保护后容量。这部分空间为介质冗余付出了开销；不同保护方式的开销不同，取决于条带宽度、副本数和可容忍故障数。全闪阵列通常选择更宽的条带或更高的纠删码比例来压低保护开销，因为闪存介质单价更高。只写"500TB 可用"而不写保护口径，等于没说明它能扛住什么故障。

第三个常被放大的数字是效率容量：重删、压缩、精简配置之后，系统显示能承载的逻辑数据量。全闪存储普遍把重删压缩作为标配卖点，有的厂商甚至把"有效容量"写在报价单上。它不是假的，但高度依赖数据特征——数据库日志可压缩性好、加密或已压缩数据几乎没有节省空间、虚拟桌面模板重复率高。同一厂商的不同产品，对逻辑空间和效率节省的统计口径都可能不同。

业务方问：那报价单上的 500TB 到底是哪个？存储团队说：如果没有写清保护方式、效率口径和统计方式，这个数字没有审批意义。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdUM9ibbYYacKyTfDkx8UPW0kPnhmoGzu1vILKBEUVQo5ibqRu5o6FJGKuSPPmhPwN3KibMm5t4rPLuX3Uuwv4ibtzYhrGRGxCmcuMA/640?wx_fmt=png&from=appmsg)一句话理解：物理容量是买来的介质，保护后容量是扣除冗余能分配的空间，效率容量是依赖数据特征的结果；三者不能互相替代。

# 保护开销不是一次性扣完就结束

业务方又问：保护开销，不是建存储池的时候就算好了吗？

存储团队说：RAID 和副本的容量代价确实在设计期就能算出来。但快照、克隆、异步复制和备份保留的空间，是随时间变化的。而且在全闪阵列上，快照带来的额外写入还会推高写入放大，间接消耗闪存寿命和 OP 空间。

快照并不等于完整复制。创建瞬间几乎不额外占空间，但父卷持续变化后会消耗增量物理块——修改越多、保留时间越长，占的空间就越多。很多全闪项目上线时快照空间充裕，三个月后运维突然发现快照把有效容量吃掉了 40%——不是因为快照有 bug，而是数据改写量远超预期，重删节省下来的空间被快照增量占回去了。

因此容量账本至少要把生产数据增长与保护数据增长拆开：谁在持续改写、保留多少个恢复点、复制是否滞后、克隆何时拆分、过期副本是否真的能按策略清理。只拿"当前数据量"乘以一个固定效率比，无法回答几个月后的可用空间。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdXZ94KxwRUleGwl46E40qfictV9Kg4FZtKfsllInbQp37op3ia9M7byGQrW43beTe7uWQXKCGBsPRwXgmyJNcS7dNF1O9zRTHpfU/640?wx_fmt=png&from=appmsg)一句话理解：保护数据不是一笔静态折扣，而是一条由变更率和保留周期共同决定的时间曲线。

# 为什么池子不能用到最后一块空间

业务方指着监控面板：还剩 8%，不是还有空间吗？

存储团队说：空间余量不只是避免告警。介质或节点故障后，系统需要把缺失数据重建到健康的资源上；扩容和数据迁移同样需要临时落点。如果池子已经接近满载，恢复动作会被限速、暂停，甚至和前台业务 I/O 互相竞争。全闪阵列虽然重建速度比机械盘快得多，但重建期间的大量写入也会推高写入放大和垃圾回收压力，同样需要留出充足的可用空间和 OP 余量。

以分布式全闪为例，系统把"接近满""回填满"和"满"分成不同阈值：达到"满"后可能直接停止写入，而"回填满"阈值关系到恢复和回填能否继续。闪存的垃圾回收还需要额外的空闲块才能高效运转，空间越满，GC 越吃力，时延波动越大。

到底留多少？没有固定百分比。余量由最坏故障域、保护方式、重建规模、恢复窗口、扩容交付周期共同决定。对承载交易且要求故障期间持续写入的系统，余量本身就是可用性设计的一部分。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdXrbicwq4zdzxlGNKLicGB79v8hslFMF4dABnLftFNIypGibWOp4aicwzjS6cU4AWPLqtyz9YrezM67foX8ibQLWpPmdJDZ1EsTnWMg/640?wx_fmt=png&from=appmsg)一句话理解：没有恢复落点的空闲空间不叫冗余；它只是还没来得及暴露的恢复风险。

# TB 没满，也可能先耗尽对象和元数据

架构师提了一个容易被忽略的点：容量规划常漏掉"非字节资源"。

海量小文件、目录项、快照数量、对象索引和文件系统元数据都会消耗资源。以文件系统为例，索引节点表在创建文件系统时就参与布局，后续难以扩展。在全闪场景下，元数据瓶颈会从"能不能存"转移到"元数据操作还能不能跟上 IOPS 预期"。

这意味着一个文件服务可能仍有大量字节空间，却因为索引节点或目录操作先触及边界。对于全闪存储，还有一层容易被忽略的：重删指纹库和压缩块映射本身也要占空间和内存，数据量越大、重删粒度越细，元数据开销越不能忽略。

![](https://mmbiz.qpic.cn/mmbiz_png/LF0nGncJCdUvYEpnLIwJFibocadH9cibYeneia8RlPqKae79XTmcHIV7ibjTkv3W5VXe3c0YNVuZYc4AK0NbvVhKrmAyQAcicszMcibUmNkvrMSeo/640?wx_fmt=png&from=appmsg)一句话理解：存储不只是在装字节；它还要管理这些字节的名字、位置、版本和关系。

# 容量审计清单：五类问题一个账本

一个能通过选型评审的容量计划，至少要同时回答下面五类问题：

要证明的事| 不能只看的数字| 还必须写清的约束与证据  
---|---|---  
**采购容量够不够**|  介质总 TB| OP 差额、保护方式、保护后口径、故障域与扩容单元  
**逻辑数据能否承载**|  重删压缩比 / 有效容量| 数据样本、效率统计口径、加密数据比例、保守情景  
**历史版本能否保留**|  快照个数| 变更率、保留期、复制滞后、克隆拆分与清理策略  
**故障时能否继续服务**|  当前使用率| 重建落点、恢复窗口、阈值、扩容周期、GC 空闲块  
**文件服务是否会先碰边界**|  已用 TB| 索引节点/对象数、元数据负载、小文件分布、指纹库开销  
  
真正需要评审的不是"现在还剩多少"，而是：下一次增长、一次保护任务和一次最坏故障同时发生时，系统是否仍有空间完成它承诺的恢复动作。
