# Q032：缓存如何提升性能，又带来哪些一致性风险？

设想一次常见的性能测试：刚开始读取很快，短时间写入也很快。测试继续运行，或者数据集扩大以后，延迟却开始上升。同一套存储、同一批服务器，为什么前后的表现不一样？

一种可能是，前半段主要测到了缓存，后半段才逐渐接近后端介质的持续服务能力。

读缓存可以省掉部分重复访问，写缓存可以吸收突发并合并部分写入；剩下必须完成的后端工作，仍要由介质承担。判断缓存是否有效，既要看它缩短了多少业务等待，也要看积累了多少回写责任，以及不同缓存能否维持正确的可见性、顺序和持久性。

这里的缓存不只是一块“缓存盘”。应用缓冲区、数据库缓冲池、操作系统页缓存、协议客户端缓存、阵列控制器缓存和硬盘内部缓存，都可能出现在同一条 I/O 路径中。它们保存的数据不同，失效条件和确认语义也不同。

# 一次读请求，可能根本没有到达存储

应用读取一段数据时，最靠近应用的缓存先判断它是否已经存在。命中后，请求可以直接从内存返回；未命中时，才继续经过文件系统、块层、网络和阵列，并可能把读回的数据留在一层或多层缓存中。

这解释了为什么反复读取一小批热点数据通常很快。真正决定收益的，是一段时间内反复访问的“工作集”能否留在缓存里。即使缓存容量很大，业务若持续扫描远大于缓存的数据集，旧数据还没再次使用便被替换，命中率仍会很低。

顺序预读利用的是另一种规律：读取当前位置时，提前取回紧邻的后续数据。连续读取大文件可能因此减少下一次等待；随机访问则可能取回大量不会使用的数据，额外占用缓存和后端带宽。SANtricity 的官方说明也把顺序预读与随机访问区别处理。

所以，缓存命中率不能单独代表业务体验。顺序读取即使命中率不高，也可能由后端高效完成；热点随机读取的命中率只下降一点，却可能把大量请求重新压到介质上。还要同时观察未命中读的时延、后端请求量和业务 P99。

# 一次写请求，为什么可以提前返回？

读缓存试图避免后端读取，写缓存则改变业务等待后端写入的时间。

在写穿策略下，请求要等数据到达策略要求的位置后再确认；在写回策略下，控制器可以先把数据放进缓存，在满足产品定义的保护条件后向主机确认，再在后台写入介质。缓存中已经更新、但后端尚未同步的数据叫作“脏数据”。“脏”表示系统仍负有回写责任，并不表示数据已经损坏。

提前确认给了控制器重新组织 I/O 的机会。相邻的小写入可能被合并；同一位置短时间内多次修改，后端可能不必保存每个中间状态；带校验 RAID 也可能利用更完整的数据范围减少部分读改写。这些收益取决于负载、实现和持久化要求，不能换算成固定的加速倍数。

# 缓存何时从加速器变成排队点？

短时突发到来时，缓存先接住数据，后端随后回写。只要突发结束后留有足够时间消化，主机就可能一直看到较低的写延迟。

持续写入时，进入缓存的有效写入速率如果长期高于回写速率，脏数据便会累积：

  * 

[code]
    脏数据变化量 = 新增有效写入量 − 已完成回写量
[/code]

在后端能力和写合并效率不变的前提下，增大缓存主要延长突发吸收时间，无法长期承接超过回写能力的写入。达到一定阈值后，系统会启动或加强回写；如果脏数据仍继续增加、可用缓存接近保护边界，才可能限制新写入并让主机等待。

于是测试出现转折：开始阶段测到缓存接收和整理写入的能力，稳定阶段才受到后端持续能力约束。诊断时应把脏数据量、回写速率、后端服务时间和主机写延迟放在同一条时间线上，而不是只看“缓存使用率”。

# 同一份数据，为什么会出现不同版本？

多层缓存最容易带来的是可见性问题。假设服务器 B 已缓存一个文件的旧内容，服务器 A 随后修改了这个文件。A 收到写入成功后，B 下一次读取是否会重新验证缓存？旧副本由谁判定失效？网络中断期间获得的锁或租约又怎样恢复？答案取决于文件协议、客户端实现、锁和应用的协作方式。

阵列能够维护自己内部缓存与后端介质的对应关系，却不知道两个应用进程对同一文件如何协作。多主机共享文件需要协议和文件锁维持访问语义；多主机直接共享同一块设备，则需要集群文件系统或应用自身的并发控制。关闭阵列缓存无法补上这些上层规则。

可见性与持久性也不能混为一谈。另一台主机已经看到新内容，不等于内容能够抵御掉电；数据已经安全保存在阵列中，也不等于另一个客户端立即放弃了旧副本。

# 写入顺序错了，数据都在也可能无法恢复

数据库和文件系统不只关心“最终都写进去”，还会依赖特定的先后关系。采用预写日志的数据库，在把修改后的数据页写入持久存储前，需要先持久化对应日志。这样即使数据页尚未写回，故障后仍能利用日志重做修改。

如果某层提前报告完成，却没有正确传递刷新和持久化要求，恢复时可能看到新的数据页，却缺少它依赖的日志。Linux 块层用 flush 推动此前的易失数据进入非易失存储，用 FUA 要求指定写入持久化后才报告完成。FUA 约束的是指定请求的完成条件；跨请求的先后关系仍需要上层按照正确顺序发出写入与刷新。

# 缓存保护状态为什么会改变性能？

写回缓存能够提前确认，前提是已确认的数据覆盖了目标故障模型。只有易失内存时，整机掉电可能丢失尚未回写的数据；数据只在一个控制器中时，单控故障可能使未完成写入无法接管。电池或电容保护、非易失日志和双控制器缓存镜像分别覆盖不同故障，不能相互代称。

当电池正在充电、保护部件故障、伙伴控制器离线或缓存规格不匹配时，系统可能暂停写缓存或改变确认路径。此时介质和容量都没有变化，业务写延迟仍可能突然上升。以 SANtricity 为例，其文档明确列出了缓存暂时停用及双控制器镜像的条件；其他产品的实际行为要以对应版本文档和事件日志为准。
