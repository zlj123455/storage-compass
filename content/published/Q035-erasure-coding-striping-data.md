# Q035：条带化、镜像和纠删码如何改变数据路径？

> 发表时间：

假设应用先写入一段对齐的 256 KiB 数据，随后只覆盖其中 16 KiB。两套都使用闪存的存储，在第一次大块写入时表现接近；处理这次小块覆盖写时，其中一套的时延却开始波动。再让保存目标数据的一个成员故障，原本很快的读取也突然变慢。

问题未必出在闪存本身。业务发出一次写入，后端可能只写一个位置，也可能把数据拆到多个成员、复制多份，或者读取旧数据后重新计算校验。条带化决定数据怎样分布，镜像和纠删码提供不同的冗余方式；它们可以组合使用，共同改变一次业务 I/O 背后的请求数量、等待对象和故障路径。

下面沿着这段数据，比较不同布局下的写入、覆盖和故障后读取。

# 条带化先决定数据落在哪里

采用条带化时，逻辑地址空间被切成固定大小的条带单元，再依次映射到不同成员。

例如，条带单元为 64 KiB，四个成员组成一个条带组。一次对齐的 256 KiB 写入可以覆盖四个条带单元，系统有机会把它们并行发给四个成员。此时，多成员确实可能提高聚合吞吐。

接着，假设那次 16 KiB 更新完整落在一个 64 KiB 条带单元内，那么仅从条带映射来看，它只命中一个成员。其他成员不会因为“阵列有四块盘”就自动参与这次请求。如果 16 KiB 的起始地址靠近边界，它也可能跨越两个条带单元，被拆成多个后端请求。

条带化提供并行机会，实际效果取决于请求大小、对齐和并发度。它本身不产生冗余，单独使用时，一个成员故障就可能使卷无法完整访问。

# 选择镜像时，一次写入变成多份

如果采用双副本镜像，这段数据及后续的 16 KiB 更新都要保存两份。镜像可以与条带化组合，但它们并非每笔请求必经的先后步骤。

读取可以选择一个有效的健康副本。多个读请求能否分散到不同副本，取决于控制器和软件的调度。

写入路径不同。同一份新数据必须送到所有要求参与确认的副本。若系统约定两个副本都进入受保护的持久化位置后才返回成功，那么完成时延会受到较慢一侧影响；若先确认、后补齐另一个副本，前台时延可能缩短，但故障窗口和数据保护语义也随之变化。

等待时间还取决于副本位于本地还是远端，以及确认点是在受保护缓存，还是最终介质。

副本也会接收误删和错误覆盖，因此镜像不能代替备份。

# 选择 4+2 纠删码时，完整写入怎样走

再看一个简化的 4+2 纠删码示例。一组数据被切成四个数据片段，系统根据它们计算两个校验片段，并把六个片段放到不同成员或故障域中。只要编码规则允许且剩余片段足够，丢失部分片段后仍能重构原数据。

这里假设四个数据片段各为 64 KiB，合计 256 KiB，两个校验片段各为 64 KiB；实际布局随实现而异。

当业务提交的数据正好组成一个完整编码条带时，系统已经拿到计算新校验所需的全部新数据。它可以切分数据、计算校验，再把六个片段写到对应位置。这类完整条带写更容易形成连续、并行的后端 I/O。

与三副本相比，4+2 保存六份片段来承载四份数据，空间开销通常更低。但节省容量并不等于减少每次写入的工作：数据需要编码，片段需要通过后端连接送到多个位置；采用跨节点部署时，这些片段还要经过网络。确认过程也要满足系统规定的成功条件，因此 CPU、后端连接和较慢的成员都可能进入写入关键路径。

# 覆盖其中 16 KiB，为什么可能先读后写？

现在，业务只修改完整编码条带中的 16 KiB。系统手上只有这部分新内容，却必须让校验结果与修改后的整条数据保持一致。

一种直接做法是读取相关旧数据，合并新内容，重新计算校验，再写回被修改的数据片段和校验片段。这就是常说的读改写。某些实现会读取旧数据与旧校验，计算差量后更新相关片段；有些实现会使用日志、缓存或聚合队列，把多个小写入凑成更接近完整条带的写入。

例如，Linux MD 的 RAID 4/5/6 实现可用写回缓存聚合小写入，减少计算校验前的旧数据读取。因此，不能把每个小写入换算成固定次数的磁盘 I/O。

协调一致性不是一句抽象要求。假如新数据已经写入，校验片段还没有更新，系统此时又突然断电，恢复时便可能面对数据与校验不匹配。实现通常需要受保护缓存、写日志或其他一致性机制，记录更新进度并在重启后完成或恢复这次写入。这些动作也会进入真实的数据路径。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdWUGXmQicnmhiaXMG0CFoLsKk2dSJSrQrgicicU1aUYicyufOxZTpkR0cwib7rdKtXSicesAVtiazuz8wPEvKFFgDhSH6OHEMCMbHpXbrg/640?wx_fmt=png&from=appmsg)

可能解释开场中的部分差异：如果其中一套采用校验保护，并且对齐的大块写入更容易被聚合成完整条带，那么 16 KiB 覆盖写触发的旧数据读取、校验更新和一致性记录就可能扩大差距。是否真的如此，还要结合缓存命中、请求合并与后端跟踪结果判断。

# 成员故障后，这 16 KiB 怎样读回来？

现在让保存目标 16 KiB 的成员发生故障，再读取刚才更新过的数据。镜像可以改从健康副本读取；纠删码若缺少目标数据片段，则需要读取足够的其他数据与校验片段，经过重构后才能返回原数据。

此时，业务看到的不一定是中断，也可能是时延升高。原本一次成员读取变成多成员读取与计算，剩余设备和网络承担更多请求。与此同时，后台恢复还会读取健康片段、重建缺失内容并写入替代位置，与前台业务争用磁盘、CPU和网络。

![](https://mmbiz.qpic.cn/sz_mmbiz_png/LF0nGncJCdVLT5uY2LEt0C4tT8wbp1T0xvLZjtr2ia7VhYpT9UibN1RdstIL3wlbibGz4X8RXe1Y3SFtusX5voRcHSXhMqrmhDCNhAjBJibibY18/640?wx_fmt=png&from=appmsg)

故障容忍能力回答的是“少了哪些成员还能得到正确数据”，不能回答“故障期间性能是否不变”。恢复速度也不能只看重建带宽：后台开得太快会挤压业务，开得太慢又会延长降级窗口，增加下一次故障到来前仍未恢复的风险。

片段放在哪里同样重要。六个片段分散在六块盘上，并不等于跨越了六个独立故障域；如果它们仍集中在同一机框、同一电源或同一站点，纠删码无法抵御这些共同故障。冗余数量必须和真正要承受的盘、节点、机框或站点故障对应起来。

# 回到那次性能差异

回看那次 256 KiB 写入、16 KiB 更新和故障后读取，差异可能分别出在并行分布、额外读改写、确认等待和重构竞争。仅凭前端时延，还不能确定是哪一段。

定位时应对照前后端请求与完成时间，观察慢请求是否伴随旧数据读取、慢副本或恢复流量。

真正值得问供应商的是：在我们的请求大小、读写比例和故障条件下，一笔写入会被放大成哪些操作，到哪一步才向主机确认成功？
