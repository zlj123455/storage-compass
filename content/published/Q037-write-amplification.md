# Q037：读写放大是如何产生的？

> 来源：存储罗盘（微信公众号）  
> 原文链接：https://mp.weixin.qq.com/s/dJuWxGjo25PBSJz_xqpP2w

> 迁移时间：2026-10-25

数据库的业务量没有明显变化，主机写入带宽也基本稳定，存储后台却突然忙了起来：后端写入量上升，SSD 磨损加快，写入 P99 开始波动。团队看着主机监控很困惑——业务明明只写了一份数据，后端为什么做了这么多工作？

因为主机提交的是逻辑请求，存储系统完成的是物理工作。一次写入可能同时触发日志、元数据、镜像或校验更新；进入 SSD 后，又可能因为垃圾回收而搬移已有数据。读取也可能为了查找元数据或重构丢失的数据块，变成多次后端读取。

读写放大，就是为完成一份逻辑 I/O，系统实际执行了更多读取、写入或数据搬移。它不是 SSD 独有的问题，而是贯穿文件系统、数据保护、快照和介质管理的结果。

所以，看到一个“放大倍数”时，先不要判断高低。更重要的是确认：它比较哪两层，统计字节还是操作次数，窗口内有没有混入重建、巡检或垃圾回收。

# 先分清：谁写了多少

SNIA 将写放大定义为设备执行的写操作超过主机请求的写操作，并指出垃圾回收和文件系统 inode 更新都可能造成放大。

统计层次| 看到的工作  
---|---  
主机层| 应用或操作系统提交的逻辑读写  
阵列层| 元数据、数据保护和后台任务产生的后端读写  
介质层| SSD 最终对 NAND 执行的写入与数据搬移  
![](https://mmbiz.qpic.cn/mmbiz_png/LF0nGncJCdWxCa7bCTPRI9QGTN3ejaibmkLPibZqGgiajkGqWBUZzic9oZtGJ75hKfprUOoIAebUh44ibQXZYTHnY4mziauN12rRSHPvl0Y1JuhnQ/640?wx_fmt=png&from=appmsg)

假设主机写入 100 个单位，阵列后端写入 180 个单位，SSD 内部最终写入 240 个单位，只能说明不同层的工作量依次增加。这些数字只是演示统计方法，不代表任何产品的典型水平。

不同计数器可能使用不同单位：有的统计逻辑字节，有的统计物理字节；有的包含后台任务，有的只计算前台请求。边界不一致，倍数就不能直接比较。

# 数据保护为什么会放大 I/O

镜像最容易理解。一份逻辑数据需要写入多个副本，额外工作换来的是成员故障后的可用性。

带校验的 RAID 或纠删码更复杂。一次没有覆盖完整条带的小块更新，可能需要先读取旧数据和旧校验，计算新校验，再写入新数据和新校验。业务发出一次写入，后端却同时增加了读取和写入。

Linux MD 文档说明，RAID 4/5/6 的非整条带写需要读取旧数据后再计算新校验；写回缓存可以聚合写入，形成完整条带后再落盘，从而避开这部分同步读取。

因此，不能把“RAID 5 小写固定放大几倍”当成通用公式。请求是否覆盖完整条带、缓存能否合并、写入是否对齐，都会改变实际代价。

读取也一样。正常状态下，系统可以直接读取目标块；成员故障后，RAID 或纠删码可能需要读取其他成员来重构数据。Ceph 官方文档也说明，纠删码池丢失的数据分片需要从其他分片恢复。

这就是为什么业务读带宽没有变化，阵列在降级期间却明显更忙。

# 日志、CoW 和快照让“小修改”不再小

应用修改一个数据块，文件系统往往还要更新 inode、空间分配、目录或校验信息。为了保证崩溃后能够恢复一致状态，这些变化还可能先写入日志。

以 ext4 为例，默认模式主要记录元数据；在 data=journal 模式下，数据和元数据都会先进入日志，之后再写到最终位置。更强的恢复保证，也意味着更多写入工作。

写时复制（CoW）又是另一条路径。系统不直接覆盖正在使用的数据块，而是写入新位置，再更新指向新数据的上层元数据。OpenZFS 文档展示了这个过程：新数据写入后，包含新指针的父节点也要更新，变化会沿树向上延伸。

这让快照可以快速创建，因为旧数据本来就被保留；代价是后续修改会产生新块、元数据更新和空间回收。快照数量增加并不意味着写放大必然按数量成倍增长，实际影响还取决于数据变更范围、保留时间和回收方式。

日志和快照造成的额外写入并非天然“不合理”。它们购买的是一致性和恢复能力。需要验证的是，这份保护是否符合业务要求，以及它的成本是否已经进入性能和容量预算。

# SSD 内部还会再搬一次数据

阵列完成后端写入后，SSD 内部仍可能产生新一层放大。

NAND 闪存通常不能原地覆盖已有内容。新数据写入空闲页，旧页被标记为无效；当可用空间减少时，垃圾回收需要先搬走擦除块中仍然有效的数据，才能擦除并重新使用这个块。

这些搬移不是主机新提交的写入，却会消耗 NAND 写入次数、后端带宽和控制器时间。SNIA 的资料指出，垃圾回收会降低性能并增加写放大；冷热数据混放也会影响回收效率。

随机覆盖写、空闲空间不足、冷热数据混合以及长时间持续写入，通常比空盘上的短时顺序测试更容易暴露介质层放大。SNIA 的固态存储测试规范因此要求进行预处理并观察稳态，而不只记录刚开始时的峰值。

# 不要把不同层的倍数直接相乘

一笔逻辑写入可能依次经过：

应用数据

→ 文件系统日志和元数据

→ 快照或写时复制

→ 镜像、RAID 或纠删码

→ SSD 地址转换与垃圾回收

这些层次可能共同增加工作，但各层倍数不能直接相乘。缓存可能合并或延迟写入，压缩和去重可能减少后端字节，后台任务又可能混入介质计数器。

NVMe 2.1 提供了一个清晰的计数边界：Data Units Written 不包含垃圾回收等控制器内部写入，Media Units Written 则包含主机和控制器写入。设备支持并上报这些字段时，两者才有条件用于观察设备内部写放大。

阵列可能不会把底层 SSD 指标直接暴露给主机，因此仍需确认产品计数器的定义，不能仅凭字段名称推断统计范围。

# 回到开场：怎样找到放大发生的位置

面对业务写入稳定、后台压力却持续上升的现象，我会先对齐同一时间窗口，再建立三层证据：

证据层| 优先核对的指标  
---|---  
主机层| 逻辑读写量、请求大小、随机性、并发度和 `fsync` 频率  
阵列层| 前后端读写量、元数据活动、快照回收、重建和巡检状态  
介质层| 主机写入与介质写入、垃圾回收、磨损、空闲空间和稳态时延  
![](https://mmbiz.qpic.cn/mmbiz_png/LF0nGncJCdUeibtqd63hFSbdzIiaOD90U9ydx0myiaDOnlIR8ibDtTgCZGGEib8ziaZhlLUe13DlIrpODafOYm1dQ7lrD4O0bNnK9R9vKtDzRzkXc/640?wx_fmt=png&from=appmsg)

如果主机与阵列后端之间的差异扩大，先检查日志、元数据、数据保护和后台服务；如果阵列后端相对稳定，而介质写入与尾时延继续上升，再重点检查 SSD 的空闲空间、垃圾回收和稳态表现。

读写放大本身不等于设计错误。镜像、校验、日志、快照和磨损均衡产生的额外工作，分别换来了可用性、一致性、恢复能力和介质寿命。

真正需要控制的，是让每一层额外工作都能被解释、被测量，并进入容量、性能和耐久预算。否则，平时隐藏在后台的物理工作，会在业务高峰、降级或空间紧张时一起暴露出来。
