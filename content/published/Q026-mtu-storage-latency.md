# 带宽没有跑满，数据库为什么还是会卡？

假设一次性能复盘：数据库提交偶尔出现时延尖峰，存储控制器和 SSD 都不忙，存储网络的平均带宽也远未达到链路上限。团队最初认为网络没有问题，直到把业务日志与交换机端口事件放到同一时间线，才发现尖峰附近出现了出口队列增长和少量丢包。

这类问题难查，是因为监控回答的是“这段时间平均传了多少数据”，业务等待的却是“这一笔 I/O 的所有必要数据什么时候到齐”。平均带宽不高，不代表某个瞬间没有排队；丢包比例很低，也不代表被丢掉的包没有落在关键 I/O 上。

MTU 决定一次 I/O 要变成多少个网络包，拥塞决定这些包需要排多久，丢包决定其中哪些包必须重新传输。三者共同影响的，不只是吞吐，更是一次 I/O 的完成时间和 P99/P99.9 尾时延。

# 一次存储 I/O 到了网络里，已经不是一个请求

应用提交的 128 KiB 写入，经过文件系统、块层和存储客户端后，可能成为一个或多个协议请求。进入网络栈后，它还要按照路径允许的报文大小分段，经过网卡、交换机队列和目标端，再由对端协议栈重组和处理。

做一个简化计算：假设使用 IPv4/TCP 且没有额外封装，MTU 为 1500 字节时，扣除常见的 20 字节 IP 头和 20 字节 TCP 头，每段大约承载 1460 字节，128 KiB 数据需要约 90 个 TCP 数据段；若端到端使用约 9000 字节的巨帧，同样的数据大约需要 15 个数据段。这个计算只用于说明数量级，TCP 选项、VLAN、隧道与存储协议头都会改变实际结果。

主机侧看到的形态还可能不同。TSO/GSO 可以先让协议栈处理较大的缓冲区，再由软件或网卡按 MSS 分段；GRO 则在接收方向合并多个报文。因而抓包位置不同，看到的“包大小”也可能不同。

# MTU 优化的是逐包开销，不是整条存储路径

在大块顺序传输或高包率场景中，更大的 MTU 可以减少相同数据量对应的帧数，降低包头占比以及逐包处理、查表和中断等压力。这也是巨帧可能改善吞吐或 CPU 利用率的原因。

但巨帧不会减少数据库锁等待、控制器排队、同步复制往返和介质服务时间。对于小 I/O 或低并发业务，能够减少的帧本来就不多，收益可能很有限。MTU 变大后，每个帧占用链路的时间也更长；它不是一个只会降低时延的开关。

真正危险的是端到端不一致。路径 MTU 等于整条路径中最小的链路 MTU。发送端生成了超过路径 MTU 的 IP 包后，系统可能依赖分片、ICMP“包太大”消息或路径 MTU 发现调整大小；如果必要的反馈被过滤，就可能出现连接能够建立、小报文正常，而大数据传输停顿的“黑洞”。

所以验证巨帧不能只看服务器网卡。主机接口、VLAN、交换端口、链路聚合、中间路由或隧道、存储前端端口，以及所有冗余路径，都必须支持相同的有效 MTU。

# 平均带宽没满，交换机队列仍可能瞬间被填满

假设多台主机同时把数据发往同一个存储前端端口。各入口都有足够带宽，但流量汇聚到一个出口后，瞬时到达速率可能超过出口发送能力。多出来的包只能进入缓冲区等待；缓冲区耗尽后，交换机开始丢包。

端口利用率通常按较长时间窗口汇总，而微突发可能只持续微秒或毫秒。它被平均值“摊平”后，图表上仍然不像链路跑满，队列却已经真实增长。对业务而言，排队时延近似取决于队列中已有的数据量和出口速率，而不是当天的平均带宽。

缓冲区也不是越大越好。更大的缓冲可以推迟丢包，却可能让包在队列中等待更久，形成缓冲膨胀。主动队列管理和 ECN 的思路，是在队列变得过长之前，通过丢包或显式标记把拥塞反馈给发送端。

# 为什么少量丢包会放大存储尾时延？

iSCSI、NFS、SMB 和 NVMe/TCP 等基于 TCP 的访问，遇到丢包后通常会由 TCP 检测并重传。可靠传输保护了字节流的完整性，却不能消除等待：缺失的数据段没有补齐之前，依赖它的协议响应无法完成；发送端还可能调整拥塞窗口。TCP 的快速重传、快速恢复和超时重传对应不同的等待尺度，因此丢包的业务影响并不与“丢包率”线性对应。

一万个请求中只有少数请求遭遇重传，平均值可能变化不大；但这些请求会进入时延分布的尾部。数据库提交、虚拟机存储和同步写通常等待完整响应，某个关键包迟到，就可能让整笔 I/O 变慢。

RoCE 走的是另一套数据路径，但也不会绕过拥塞。PFC 可以按流量类别发送暂停，目标是减少拥塞导致的帧丢失；ECN 则允许设备在队列开始增长时标记报文，让端点降低发送速率。两者处理的问题不同，而且需要网卡、交换机、优先级、队列和端点算法协同。PFC 不是所有 RoCE 部署的唯一答案，开启它也不等于没有排队、暂停扩散或配置风险。

# 排查时，要把六层证据放到同一时间线上

先从业务侧确定尖峰发生的时间、请求类型和 P99，而不是从交换机上漫无目的地找异常。随后依次关联：主机 TCP 重传、RTT 或 RDMA 计数；网卡丢弃、错误和流控；交换机出口队列、丢包、ECN 标记与暂停帧；存储前端端口事件；控制器队列和介质时延。

如果业务变慢时介质正常，而交换机出口队列与主机重传同时上升，网络拥塞的证据链才成立。如果只有一个累计丢包计数，却不知道它何时发生、属于哪个端口和流量类别，就不能据此给存储网络定责。

MTU 也要沿真实数据路径验证。普通ping能通只证明小报文可达；应使用操作系统支持的禁止分片或指定报文大小方式，分别检查每条业务路径，并结合抓包确认线上帧、MSS、重传和 ICMP 反馈。具体命令与可观察计数因操作系统、网卡和交换机实现而异。

回到开头的复盘：带宽未满只能说明统计窗口内没有持续跑满，不能排除微突发；少量丢包也不能因为比例低而忽略。最终要回答四个问题：等待来自逐包处理、排队还是重传？异常出现在平均值还是尾部？MTU 是否在每条路径上真正一致？网络事件是否与业务尖峰发生在同一时间？

只有把这些证据放回一次真实 I/O 的时间线，MTU、拥塞和丢包才不再是孤立的网络指标，而能解释业务为什么变慢。
